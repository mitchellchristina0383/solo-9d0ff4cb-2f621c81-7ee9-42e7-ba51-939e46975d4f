# 磁带机取回模拟器（tape-drive-sim）

用 FastAPI 模拟一台磁带机：接收待取文件清单和副本目录（至多 12 卷），
给出**装带 + 回卷总次数最少**的读取顺序；值班员逐步回报读带结果，
系统按带头新位置重排剩余文件，并列出已无副本可读的文件。

支持**掉电重启续作**：所有变更写盘成功后才生效；重启后若仍有待取文件，
作业先暂停（停发读带步骤、拒收回执、进度可查），值班员在 `/docs` 上报
实际挂载卷号与带头位置（或确认空机）后，按实测位置重排并保留全部已入账进度。

## 运行

```bash
docker compose up --build      # 服务监听 8000 端口
# 浏览器打开 http://127.0.0.1:8000/docs （Swagger UI）逐步操作
```

本地开发（无 Docker 时）：

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --port 8000
.venv/bin/pytest tests/ -q                    # 单元/集成测试
.venv/bin/python scripts/walkthrough.py       # 对运行中的服务走一遍完整取回流程
```

## 实现

### 代价模型（与值班室约定）

- **装带**：挂载一卷计 1 次；当前已挂载的卷继续读不计；装带后带头在卷首。
- **读带**：只能向序号增大方向读；同卷内按序号升序读不需要回卷。
- **回卷**：在当前卷上需要读比带头位置更小的序号时，回卷 1 次（回到卷首再升序读）。
  因此每卷至多回卷 1 次，且只有“当前已挂载卷”可能被迫回卷。

### 规划算法（`app/planner.py`）

卷数 ≤ 12，**精确枚举**所有非空卷子集（≤ 4095 个）：

1. 子集须覆盖全部待取文件（每文件至少一个可用副本落在子集内）；
2. 代价 = 装带数 + 回卷数。装带数 = 子集卷数（当前卷在子集内则减 1）；
   回卷 = 1 当且仅当某文件在子集内的副本**全部**落在当前卷且全部低于带头；
3. 取代价最小者；平局依次按装带更少、用卷更少、位掩码更小裁决（确定性）；
4. 副本指派：优先非当前卷的副本，其次当前卷带头之后的副本，最后才回卷读；
   读取顺序：当前卷最先（避免卸下再装），卷内升序，当前卷低于带头的部分
   排在回卷动作之后。

### 交互协议（`app/main.py` / `app/state.py`）

| 接口 | 说明 |
| --- | --- |
| `POST /jobs` | 创建取回作业（文件清单 + 副本目录），写盘成功后生效，返回初始状态与最优计划 |
| `GET /plan` | 按当前带头位置重算最优计划，`next_step` 即下一步要回报的读带步骤；暂停期间不发步骤（`steps=[]`） |
| `POST /receipts` | 回报**当前计划第一步**的读带结果（`ok` / `failed`），写盘成功后入账并重排 |
| `GET /state` | 作业状态（active/paused）、当前卷、带头位置、待取/已取/无副本文件、停用副本、累计执行次数 |
| `POST /resume` | 掉电重启后上报**实测**卷号与带头位置（`volume=null,head=0` 表示确认空机），确认后续作并重排 |
| `DELETE /job` | 作废当前作业，写盘成功后生效；重启后仍按无作业处理 |

规则落实：

- **只用当前计划第一步的回执更新进度**：不符的回执返回 409 并附上期望步骤，状态不变；
- **失败也推进带头**：成功或失败，带头都推进到该步骤的卷内序号（跨卷步骤视为装带已发生）；
- **停用出错副本**：失败副本立即从目录中停用，不再参与后续规划；
- **每步重排**：每张回执生效后按新带头位置重新规划，响应中列出已无副本可读的文件。

### 持久化与掉电恢复（`app/state.py`）

- **状态快照**：整份作业（文件清单、副本启停、已取集合、当前卷/带头、累计计数、
  回执历史、状态位）序列化为一个 JSON 文件，路径由环境变量 `TAPE_STATE_FILE` 指定
  （默认 `./tape_state.json`；Compose 中固定为挂载卷里的 `/data/tape_state.json`）。
- **原子写盘**：写临时文件 + `fsync` + `os.replace`，中途掉电只会留下旧文件或临时文件，
  不会出现半截 JSON。
- **写盘成功才生效**：创建/作废作业、应用回执、确认卷位都先在深拷贝上计算并落盘，
  写盘抛错时返回 HTTP 500，内存记录与磁盘旧快照都保持原样；重启只恢复最后一次写盘成功的记录。
- **重启即暂停**：进程启动加载快照，只要还有待取文件（含已无副本可读的文件），
  作业一律进入 `paused`：
  - `GET /state` 仍可查全部已入账进度；
  - `GET /plan` 返回空步骤、`next_step=null`（停发读带步骤），仅保留无副本清单；
  - `POST /receipts` 一律 409 拒收（暂停期间不接收任何回执）；
  - 变更类接口（`POST /jobs` 除外——它是显式开新作业）同样被暂停态挡下。
- **确认续作 `POST /resume`**：值班员按驱动器实测情况上报 `{volume, head}`，
  或 `{volume: null, head: 0}` 确认空机（空机配非零带头返回 422）。
  确认后写盘并切回 `active`，规划器按实测位置重排；已取文件、停用的坏副本、
  累计装带/回卷/成功/失败计数、回执历史全部保留。
- **作废即持久化**：`DELETE /job` 把快照写成 `null`，容器重建后加载为无作业（404）。
- **重建容器可续作**：Compose 把状态目录挂成命名卷 `tape-state`，容器重建不丢卷；
  已作废的作业快照为 `null`，重建后仍按无作业处理。
- 无待取文件的作业重启后不暂停（无需确认卷位），此时对其调 `/resume` 返回 409。

  无待取作业重启不暂停、无副本文件仍算待取故仍暂停、多次重启持续暂停直到确认。

- 走查：
  - `scripts/walkthrough.py` 对运行中的服务完整走一遍取回流程（与 /docs 同一套 API）：
    初始计划 2 装带 0 回卷 → 乱序回报被拒（409）→ A 的两个副本先后读失败
    （带头推进、副本停用、每步重排）→ A 进入无副本清单 → B/C/D/E/F 全部取回，
    累计装带 3 次、回卷 0 次。
  - `scripts/restart_walkthrough.py` 验证掉电续作（两个阶段，中间重启进程）：
    阶段 1 建作业并回报两步；重启后阶段 2 自查暂停语义（`/plan` 空步骤、回执 409）、
    空机非法参数 422、确认空机后续作跑完，已取/坏副本/计数保留，重排后总装带 3 次。
- **实测记录（本机执行）**：
  - 用 uvicorn 真实进程 + `TAPE_STATE_FILE` 独立数据目录完成“建作业→回执→杀进程→重启”：
    重启后 `status=paused`、卷位/已取/坏副本/计数完整恢复；`/resume` 上报实测卷位后
    按新带头重排（实测带头前移到 6 时 B@1:6 直接可读，无需回卷）。
  - **真实写盘失败**：把数据目录置为只读（`chmod 555`）后，`/resume`、`/receipts`、
    `DELETE /job`、`POST /jobs` 全部返回 500，作业仍为暂停、磁盘快照字节不变；
    恢复写权限并重启后，加载的仍是最后一次写盘成功的旧记录，随后写盘恢复正常。
  - 作废作业后快照内容为 `null`，重启后 `/state`、`/resume` 均 404，新建作业正常。
- 本环境无 Docker 守护进程，`docker compose up` 未在本机执行；
  `docker-compose.yml` 已通过 YAML 校验：命名卷 `tape-state` 挂到 `/data`，
  `TAPE_STATE_FILE=/data/tape_state.json`，容器重建后卷数据保留即可续作；
  运行期行为以本地 uvicorn 进程级重启测试（与容器重建同构：卷保留、进程重建）验证。

## 遗留事项

1. **实际流程中回卷永不触发**：计划按升序调度且失败副本即停用，
   “当前卷上存在带头之下的可用副本”这一回卷前提在回执流中不可达
   （不变式见 `test_live_flow_never_needs_rewind` 注释）。
   回卷分支仅为理论完备性保留（如初始状态允许带内定位、或未来支持指定初始卷）。
2. **单作业模型**：同一时刻只保留一个取回作业，`POST /jobs` 会覆盖旧作业；
   多作业并行需要引入作业 ID 与分文件存储。
3. **状态文件无并发写保护**：原子替换保证单进程下不损坏，但若多实例共享同一卷文件，
   需要额外加文件锁；当前 Compose 只部署单副本。
4. **损坏快照的处置**：启动时若 JSON 解析失败会直接抛错阻止启动（宁可不起，不静默丢作业），
   尚未提供管理员侧的备份/修复入口；现场可手工移走损坏文件后重启（按无作业处理）。
5. **装带/回卷视为必然成功**：真实驱动器可能有机械故障，模型未覆盖。
6. **同位置多副本**：允许不同文件登记相同 (卷, 序号)，视为先后可读（带头语义为
   “最后读到的序号”，同序号可连续读）；如需严格物理语义可改为带头 = 序号 + 1。
7. **无鉴权**：默认内网值班室使用；对外暴露需自行加认证。
